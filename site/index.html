The gap

Your agent says it's done.
Can it prove it?

Today's spec-driven tools split the job in two. Neither checks that the code actually satisfies the spec. The link between a scenario and the test that proves it lives only in a prompt.

Spec tools
Manage what to build

Spec Kit and OpenSpec turn intent into durable Markdown. Great specs, but nothing checks the code against them.

Discipline tools
Manage how the agent works

Superpowers nudges the agent toward TDD by prompt. Helpful, but a prompt is a request, not a guarantee.

Nobody
Checks the spec was built

Combine them and you get two competing workflows, more ceremony and more tokens, and still no proof.

Three promises, enforced by a binary

Verification, not vibes.

specjutsu does deterministically, in the binary and in CI, what other tools hand to the model.

Proof, not promises

Every spec scenario is traced to a test. A scenario with no test, or a test pointing at a scenario that no longer exists, blocks the merge.

Red first, for real

CI runs your new tests against the old code. If they already pass there, they didn't drive the change, and the gate says so.

Fewer tokens

If a program can decide it, the binary does it and hands your agent a few lines, not whole folders and raw test logs.

How it works

One ID joins spec and test.

Plain Markdown delta specs plus one convention: a stable ID at the start of each scenario. An existing OpenSpec repo that follows it is already a specjutsu repo.

01 · spec

Name the scenario

Give every scenario a stable ID like AUTH-003.

#### Scenario: AUTH-003 Reject expired token
- **WHEN** the client calls GET /me
  with a token issued 25 hours ago
- **THEN** the response is 401
  with code TOKEN_EXPIRED
02 · test

Reference it from a test

By test name, title or a comment above it, in Rust, TypeScript or Python. No library needed.

// vitest, Jest, Playwright
it("AUTH-003 rejects expired token", …)

# pytest
def test_auth_003_rejects_expired(): …

// Rust
fn auth_003_rejects_expired_token() { … }
03 · prove

Trace it and gate it

See every gap locally, then let CI refuse anything unproven.

$ sj trace
trace: 3 mapped, 1 gaps, 1 orphans, 0 without ID

        (specjutsu/specs/auth/spec.md:31)
orphan  AUTH-009 ← tests/auth.rs

The moat · red-on-base

A test that passes on the old code didn't drive the change.

That's the check no other spec-driven tool makes. sj gate proves your tests were red before they were green, in CI, every pull request.

  • Checks out the base commit and overlays only the change's test files.
  • Requires each new test to fail there, then pass on the PR head.
  • Bounded cost: only the changed tests run twice.
  • Honest escape hatches: refactors and chores declare an exemption with a one-line reason, shown in the PR.
base
old code+ new tests
✗ RED
PR head
new code+ new tests
✓ GREEN 
$ sj gate --base origin/main
gate: fail — 1 problem
green-on-base AUTH-007 auth_007_rejects_reused_token

Exit codes: 0 pass · 1 fail · 2 error. Drop it into any CI.

Built for agents

Your agent's sensei.

specjutsu never calls an LLM. It's the deterministic referee your agent reports to, and CI calls the same binary, so local and CI results always agree.

  • Failures-only output: a green run prints one line; a red run shows only the failing tests and their scenarios.
  • Machine-readable everything: every command takes --json.
  • Can't be talked around: where a tool can't block an edit, the CI gate still refuses unproven work.
  • TDD at the keyboard: a pre-edit hook blocks source edits until the active task's scenarios have a failing test.

Quickstart

From install to a blocking gate
in a few minutes.

One command on macOS, Linux and Windows, or Homebrew and Cargo. Every install is checked against the release's SHA256SUMS.

1Install

One binary, no runtime. The installer picks your platform and verifies the download.

# macOS and Linux
curl -fsSL https://nabour-labs.github.io/specjutsu/install.sh | sh

# Windows (PowerShell)
irm https://nabour-labs.github.io/specjutsu/install.ps1 | iex

# or Homebrew (7+ asks you to trust the formula first), or Cargo
brew trust --formula nabour-labs/tap/specjutsu
brew install nabour-labs/tap/specjutsu
cargo binstall specjutsu

# check it
sj --version

2Adopt and trace

Detect your runners, give every scenario an ID, see what has tests.

sj adopt          # write specjutsu.toml
sj ids --write    # add scenario IDs
sj trace          # list gaps and orphans
sj spec infer tests/  # draft specs from untraced tests (next release)
sj init --agents claude  # skills + hooks

# or replace your old tool in one go
sj migrate --from openspec --write

3Gate every PR

Blocks merges that can't prove red-on-base, then green.

# .github/workflows/ci.yml
- uses: actions/checkout@v4
  with: { fetch-depth: 0 }
- uses: nabour-labs/specjutsu@v0
