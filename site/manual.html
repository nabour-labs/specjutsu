User manual · v0.6.0

Using specjutsu

Everything you need to go from an openspec/ folder, a Spec Kit project or a Superpowers setup to pull requests that can't merge unless every scenario is tested and every test was red first.

What works today

specjutsu is pre-alpha and built in the open; the beta opens once specjutsu has fully replaced OpenSpec and Superpowers in our own production monorepo. This manual marks every feature with its state, so you know what you can rely on.

In practice today: specjutsu runs the whole loop on its own, from sj spec new to sj spec archive. You don't need OpenSpec, Spec Kit or Superpowers alongside it, and sj migrate removes them for you.

Install

One binary, no runtime. The installers download the latest release for your platform, check it against the release's SHA256SUMS and install sj.

# macOS and Linux: installs into ~/.local/bin and prints the PATH line if it's missing
curl -fsSL https://nabour-labs.github.io/specjutsu/install.sh | sh

# Windows: installs into %LOCALAPPDATA%\Programs\sj and adds it to your user PATH
powershell -ExecutionPolicy ByPass -c "irm https://nabour-labs.github.io/specjutsu/install.ps1 | iex"

# Homebrew (macOS and Linux)
brew install nabour-labs/tap/specjutsu

# Cargo: binstall downloads the release binary, install builds from source
cargo binstall specjutsu
cargo install specjutsu

sj --version

Both installers read SJ_VERSION (a release such as 0.6.0, default the latest) and SJ_INSTALL_DIR. install.ps1 also reads SJ_NO_MODIFY_PATH=1, which leaves your PATH alone. install.sh never edits shell profiles. To update, run the installer again or brew upgrade specjutsu.

The archives are on the releases page:

Let your agent install it

The specjutsu setup skill takes an agent from no sj to a checked setup: it installs sj (asking first), runs sj adopt on an existing project or sj init on a new one, installs the adapters with sj init --agents auto, and ends with sj doctor and sj status. On a project with tests it offers sj spec infer to draft their scenarios. It never replaces an existing specjutsu.toml. Add it with the skills CLI (in Claude Code it is also the /specjutsu command), or paste the prompt into any agent:

npx skills add nabour-labs/specjutsu --skill specjutsu

# or tell any agent:
Set up specjutsu in this project: read
https://raw.githubusercontent.com/nabour-labs/specjutsu/main/skills/specjutsu/SKILL.md
and follow it.

Shell completions

sj completions <shell> prints a completion script for bash, zsh, fish, powershell or elvish, built from the binary's own commands and flags. It writes no file: save the output where your shell looks, and regenerate it after upgrading.

# bash
sj completions bash > ~/.local/share/bash-completion/completions/sj
# zsh: then add fpath=(~/.zfunc $fpath) before compinit in ~/.zshrc
mkdir -p ~/.zfunc && sj completions zsh > ~/.zfunc/_sj
# fish
sj completions fish > ~/.config/fish/completions/sj.fish
# elvish: then add `use sj` to ~/.config/elvish/rc.elv
sj completions elvish > ~/.config/elvish/lib/sj.elv
# PowerShell: add this line to $PROFILE
sj completions powershell | Out-String | Invoke-Expression

Update or reinstall

Install over the old binary: --force replaces the sj already in ~/.cargo/bin. With a prebuilt archive, download the new release as above and run install again.

# the latest release, from crates.io
cargo install specjutsu --force

# a fix that is merged but not released yet, from main on GitHub
cargo install --git https://github.com/nabour-labs/specjutsu --branch main specjutsu --force

# which build is installed, and where it came from
cargo install --list | grep -A1 specjutsu

sj --version names the build. One made from a git checkout, including cargo install --git, prints the short commit after the version, such as sj 0.6.0 (f62a48b). One from crates.io or a release archive prints only the version. cargo install --list also names the source: a build from GitHub shows the repository URL and commit in brackets after the version.

Agent hooks call sj from PATH, so sessions that are already open use the new binary on their next edit, with no restart. Then run sj update in each project, so the generated skills, hooks and agent instructions match the new version. Files you edited by hand are kept and reported.

Set up a project

Pick the line that matches where you're starting from. Each one writes specjutsu.toml, which says where the specs are and which packages and test suites the project has.

# a new project
sj init --agents claude

# an existing project without a spec tool
sj adopt --dry-run        # print the detected packages and runners
sj adopt
sj init --agents claude

# a project on OpenSpec, Spec Kit or Superpowers
sj migrate --from openspec --from superpowers           # dry run; --diff shows each file's diff
sj migrate --from openspec --from superpowers --write   # needs a clean git tree
sj migrate --undo                                       # put back what the write changed

# then check it
sj doctor

sj adopt reads Cargo, pnpm, npm and yarn workspaces and pyproject.toml, and detects cargo, vitest, jest, pytest and playwright without running anything. For each non-Cargo suite it declares the package's test helper folders as support globs, such as support = ["apps/api/src/__fixtures__/**", "apps/api/src/testing/**"], so the gate overlays them on base, and notes each glob it adds. Support files aren't source and are overlaid on base, so don't mark product code as support. sj doctor lists config errors, packages without a runner, runners that aren't installed and missing spec folders.

# specjutsu.toml, as sj adopt writes it for a pnpm app with a uv worker
schema = 1
spec_root = "specjutsu"
mode = "guided"

[[package]]
path = "apps/app"
sources = ["apps/app/**"]

[[package.suite]]
runner = "vitest"
tests = ["apps/app/**/*.{test,spec}.{ts,tsx,js,jsx,mts,cts}"]
setup = "pnpm install --frozen-lockfile"

[[package]]
path = "python/worker"
sources = ["python/worker/**"]

[[package.suite]]
runner = "pytest"
tests = ["python/worker/**/test_*.py", "python/worker/**/*_test.py"]

mode sets how strict the agent loop is: strict refuses to tick a task until its scenarios are proven, guided warns, advisory only reports. The CI gate is the same in every mode.

Specs from existing tests

An existing project has tests that no scenario describes. sj spec infer drafts one [keep] scenario per untraced test (no scenario ID in its name, title, spec: comment or marker), so the behaviour those tests already prove is written down and gated. Start with a dry run on one area a reviewer can judge; it writes nothing:

$ sj spec infer tests/refunds.rs --capability refunds
REFUNDS-001 [keep] Refund under 100 auto approves  (tests/refunds.rs:4)
REFUNDS-002 [keep] Refund over limit needs review  (tests/refunds.rs:10)
2 tests drafted, 1 linked left out

Linked tests and tests marked skip, todo, fixme or #[ignore] are left out and counted. Without --capability, the capability is the nearest folder above the test that isn't a test or source folder. Then write the change, fill in the scenarios and gate it:

$ sj spec infer tests/refunds.rs --capability refunds --write   # changes/infer-refunds/ and a spec: comment above each test
REFUNDS-001 [keep] Refund under 100 auto approves  (tests/refunds.rs:5)
REFUNDS-002 [keep] Refund over limit needs review  (tests/refunds.rs:12)
2 tests drafted, 1 linked left out
created specjutsu/changes/infer-refunds
# ask your agent to replace each [NEEDS CLARIFICATION] marker from the test it names (sj-propose does this)
$ sj spec check infer-refunds    # until no clarify lines remain
$ sj gate --base origin/main     # REFUNDS-001 and REFUNDS-002 pass as green:keep

The tests only gain a comment, so they pass on base and at head, which is what [keep] asks. Each comment moves the tests below it down a line, so the lines --write prints and the markers name are the lines the tests are on afterwards. See sj spec infer for headings, IDs and the files it writes.

Core concepts

Where specs live

Current truth lives in specjutsu/specs/; in-flight changes live in specjutsu/changes/<change>/; the archive is read for IDs and never written. Set spec_root in specjutsu.toml (or pass --spec-root) if your folder has another name. A project with only an openspec/ folder keeps using it.

specjutsu/
  principles.md                      # project rules the agent reads
  specs/auth/spec.md                 # current truth
  changes/add-token-expiry/
    proposal.md                      # why, scope, exemptions
    design.md
    specs/auth/spec.md               # ADDED / MODIFIED / REMOVED / RENAMED
    tasks.md                         # each task names its scenario IDs
  changes/archive/

Every scenario gets a stable ID

Each scenario name starts with an ID of the form PREFIX-NNN, one prefix per capability, never reused. Matching ignores case and treats - and _ the same, so AUTH-003 matches auth_003.

### Requirement: Expired tokens are rejected
The system SHALL reject tokens older than 24 hours.

#### Scenario: AUTH-003 Reject expired token
- **WHEN** the client calls GET /me with a token issued 25 hours ago
- **THEN** the response is 401 with code TOKEN_EXPIRED

A scenario that must hold for every input starts with a FOR ALL step, before WHEN. It needs a property test: one inside a Rust proptest! { … } block or with #[proptest], a Python test with @given(…) in a file that imports hypothesis, or a TS/JS test that calls fc.assert(, fc.property( or fc.asyncProperty( where fc is a default, namespace or require import of fast-check. specjutsu reads the test source to tell; it never runs the library itself. Aliases of named imports, re-exports, @fast-check/vitest's test.prop, a callback passed by reference and proptest!(|..| ..) inside a plain #[test] aren't detected.

#### Scenario: PAY-020 Refund never exceeds the charge
- **FOR ALL** charges and refund requests
- **WHEN** a refund is issued
- **THEN** the refunded total is at most the charge

Existing specs don't need editing by hand. sj ids --write adds IDs to every scenario without one, changing only the headings. Prefixes come from the capability folder (user-auth → USERAUTH) unless you map them under [ids.prefixes], and a delta copy in an open change gets the same ID as its spec. sj ids --write staff limits the write to one capability.

Tests point at scenarios

Link a test by putting the ID in its name or title, or in a spec: comment on the line above. No library needed.

// vitest, Jest, Playwright: the title, a describe title, or a comment
it("AUTH-003 rejects expired token", () => { … })

describe("AUTH-004 refresh", () => {
  it("issues a new token", () => { … })   // covered by AUTH-004
})

# pytest: the function name, a marker, or a comment
def test_auth_003_rejects_expired(): …

@pytest.mark.spec("AUTH-005")
def test_rotates_key(): …

// Rust: the function name or a comment
// spec: AUTH-006
#[test]
fn rejects_token_issued_yesterday() { … }

Titles built at runtime (variables, ${} templates) aren't read; use a spec: comment for those.

Red-on-base

The gate's core check. It checks out the base commit, overlays only the change's test files, and runs the new tests there. They must fail. Then they must pass on the PR head. A test that already passes on the old code didn't drive the change.

  • It runs per suite. Every changed file matching a suite's tests or support globs is overlaid, so a co-located auth.test.ts runs against the base auth.ts.
  • An assertion failure on base counts as red (red:assert). A test that fails to compile or load, because it calls code that doesn't exist yet, counts too (red:compile).
  • A test that fails to load on base because it imports a test helper the change added or modified, but no support glob overlaid, fails as not-overlaid, not red:compile. Helpers are files under a testing, test-utils, test-helpers, testutils, fixtures, __fixtures__, mocks or __mocks__ folder, found by path in the base failure message with \ or / as the separator (non-Cargo suites only). A new source module that base can't load is still red:compile.
  • A suite with red_on_base = "assert" counts only assertion failures: a compile or load failure there fails as compile-red. It takes no reason and works for Cargo suites too.
  • An implemented scenario, one that existed before and gains its first test, whose tests pass on base and at head is green:linked: the behaviour predates the change and the test only links to it. It passes, but doesn't count as specifying a source change, even when its test then fails at head. When one of its tests fails on base, that failure proves it instead.
  • A base checkout has no installed dependencies, so a suite can declare setup (e.g. pnpm install --frozen-lockfile), run once before its base run.
  • A suite that can't run on old code, such as end-to-end tests against a deployed API, sets red_on_base = "skip" with a reason. Its new tests are unverifiable, and its head run still happens.
  • Rust tests inline in source files (#[cfg(test)] mod tests) can't be overlaid and are reported as unverifiable. Keep scenario tests in tests/.

The evidence ledger

sj test appends one line per test to .specjutsu/ledger/runs.jsonl: run ID, time, git tree hash, test, scenario IDs and result. It's gitignored and local. A scenario is proven when a failing run was recorded before a passing one, on different code. The agent loop and the pre-edit hook read it; CI never trusts it and recomputes red and green itself.

Your first proven change

The full loop with sj alone. The same steps work whether you type them or your agent does; with the Claude Code adapter, the sj-propose, sj-apply and sj-finish skills run them for you.

  1. Create the change

    $ sj spec new add-token-expiry
created specjutsu/changes/add-token-expiry
next AUTH-003

    Write proposal.md, the delta spec under specs/, design.md and tasks.md. Each task names the scenarios it covers: - [ ] 1.1 Reject expired tokens (AUTH-003).

  2. Check the plan

    sj spec validate add-token-expiry   # format, IDs, deltas, task links
sj spec check add-token-expiry      # uncovered scenarios, open questions

  3. Write the failing test first, and commit it

    sj next prints the task, its scenario text and the test command. Add the test, watch it fail, and commit it on its own:

    $ sj test AUTH-003
test: fail — 1 failed, 0 passed
fail    src/auth.test.ts › AUTH-003 rejects expired token  AUTH-003
git commit -m "test(AUTH-003): red"

  4. Make it pass

    Implement until the test is green, tick the task and commit:

    sj test AUTH-003
sj task done add-token-expiry 1.1   # strict mode needs red-before-green
git commit -m "feat(AUTH-003): green"

    The test(ID): red / feat(ID): green commit pair lets sj gate --since check red-before-green from history later.

  5. Verify and open the PR

    $ sj verify
verify: ok
$ sj gate --base origin/main        # what CI will run
gate: pass — 1 scenario proven (1 red:assert)

  6. Archive

    After merging, fold the delta into current specs:

    sj spec archive add-token-expiry   # → changes/archive/YYYY-MM-DD-add-token-expiry/
sj spec archive --all-done         # every change whose tasks are all done, as one operation

Set up your agent

specjutsu never calls an LLM. Your agent runs sj like any other command and gets a few lines back.

sj init --agents claude          # install
sj update                        # regenerate; hand-edited files are kept
sj update --dry-run              # preview each write, keep and remove; change nothing
sj init --remove-agents claude   # remove everything it added

The Claude Code adapter writes three things and touches nothing else:

  • A block in CLAUDE.md between <!-- specjutsu:begin --> and <!-- specjutsu:end -->, under 1,200 bytes.
  • Ten skills under .claude/skills/sj-*/: explore, propose, clarify, principles, apply, debug, review, verify, finish and onboard. New to specjutsu? Ask your agent to onboard you: sj-onboard runs one toy change through the whole loop in a scratch change, sj-onboard-demo, then deletes it without archiving, so your specs are unchanged. It won't start on a dirty working tree.
  • Two hooks in .claude/settings.json, added after yours. The file is edited as text, so your formatting, permissions and other hooks stay byte for byte.

sj hook claude session-startPrints the sj status lines and the active task, in at most 1,200 bytes.
sj hook claude pre-editBefore Edit, Write, MultiEdit and NotebookEdit on a source file, blocks the edit until each scenario of the active task has a red run in the ledger. Tests, specs and docs are always allowed. advisory mode only warns.

Skills. Codex, Gemini CLI and Antigravity load skills from .agents/skills/, so installing any of them writes the ten sj-* skills there beside .claude/skills/. sj update keeps both copies in step; removing the last of the three removes the sj-* skills and keeps yours. --global on sj init, sj update and --remove-agents acts on ~/.claude/skills/ and ~/.agents/skills/ instead and writes nothing in the repository. sj doctor prints skills: project, global or project, global.

Whatever the agent does, sj gate in CI refuses unproven work. Hooks stop it earlier; the gate is the backstop.

Gate every pull request

Add the specjutsu action, published on the GitHub Marketplace as specjutsu gate. It installs a pinned sj (verified against the release's checksums), runs the gate against the PR's base, writes the job summary and keeps one PR comment up to date. It needs the full history (fetch-depth: 0) to check out the base commit, and the toolchains your suites use (Rust, Node, uv) to run tests on both sides.

# .github/workflows/specjutsu.yml
on: pull_request
jobs:
  gate:
    runs-on: ubuntu-latest
    permissions: { contents: read, pull-requests: write }
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      # set up your toolchains and install dependencies here
      - uses: nabour-labs/specjutsu@v0

Inputs: fail-on: never reports without failing the step, comment: false writes only the job summary, and badge: true (on pushes to the default branch, with contents: write) publishes a spec coverage badge to the sj-badge branch. Other CI systems can run sj gate --base origin/main directly, or --format markdown for the comment body.

Not ready to gate? Start with a report: sj trace | tee -a "$GITHUB_STEP_SUMMARY" prints coverage on every run without failing it. Add --strict when you want gaps to fail. With a trace baseline, --strict fails only on new gaps and orphans and on stale baseline entries.

The hint names the property library for the test's suite: proptest (Cargo), Hypothesis (pytest), fast-check (vitest, Jest, Playwright); for a JUnit suite, by the test file's extension (.rs proptest, .py Hypothesis, JS/TS fast-check). The gate fails closed: any changed file is source unless it's a test, a spec, documentation or media, repository metadata (.github/, .gitignore, LICENSE) or a manifest or lockfile. When a package declares sources, only files matching them count, and a top-level non_source = ["infra/**"] adds your own globs. With no test suite configured, the gate exits 2 and suggests sj adopt instead of passing changes it can't test.

Unchanged scenarios without tests show up as warnings, not failures, so you can adopt specjutsu in an existing repo and tighten coverage as you go. A commit that only adds IDs counts as unchanged.

Adopting a baseline

A repo with thousands of old gaps, or old orphans that would fail every PR, records them once in <spec_root>/trace-baseline.txt. sj trace --write-baseline writes every current gap and orphan, one sorted entry per line, and replaces any earlier file:

$ sj trace --write-baseline
baseline: 3 entries → ./specjutsu/trace-baseline.txt
$ cat specjutsu/trace-baseline.txt
gap AUTH-002
gap AUTH-005
orphan AUTH-009 tests/auth.rs auth_009_old

An orphan is keyed by its ID, test file and test name. Test file paths with spaces aren't supported: such an orphan never matches its line, so it always counts as new. With a baseline, sj trace lists only the entries it doesn't hold and counts the known ones, and reports entries that are no longer true as stale:

$ sj trace --strict
trace: 2 mapped, 2 gaps (1 known), 1 orphan (1 known), 1 without ID
gap     AUTH-006 Expired  (specjutsu/specs/auth/spec.md:23)
stale gap AUTH-002 (remove from trace-baseline.txt)

--strict exits 1 only for new entries and stale ones, so CI notices both new debt and lines left behind. In --json, each gap and orphan carries "known", and a stale array lists stale entries as their baseline lines.

The gate reads the baseline as it is on the merge base:

  • Known gaps collapse into one warning, known gaps: 2981 (trace-baseline.txt).
  • Known orphans don't fail the gate.
  • Added, modified and newly implemented scenarios are gated as before, listed or not.
  • Stale entries are stale gap AUTH-002 warnings and never fail the gate. Run sj trace --strict in CI to enforce the cleanup.
  • Entries the PR adds fail as baseline-added <entry>, so a PR can't hide its own orphans. With a config exemption they're honoured and listed as warnings.

So the first baseline lands in its own commit, with the exemption as a trailer:

sj trace --write-baseline
git add specjutsu/trace-baseline.txt
git commit -m "chore: adopt trace baseline" -m "Specjutsu-Exempt: config — adopt trace baseline"

# its gate run
gate: pass — no changed scenarios to prove
warn    baseline-added gap AUTH-002
warn    baseline-added gap AUTH-005
warn    baseline-added orphan AUTH-009 tests/auth.rs auth_009_old
warn    known gaps: 2 (trace-baseline.txt)
exempt  config — adopt trace baseline

Exemptions

Some changes don't add behaviour. Declare them explicitly, with a reason. Every exemption appears in the gate summary.

# in the change's proposal.md
Exempt: refactor — extract token parser

# or, for changes without a change folder, as a commit trailer
Specjutsu-Exempt: chore — bump dependencies
KindEffect
refactor, docs, config, choreNo scenario required and no red-on-base. When source files change, the full test suite still runs at head and must pass.
spikeAllowed on spike/* branches; blocked from merging to main.

Command reference

Exit codes are shared: 0 pass, 1 fail, 2 usage or environment error. Most commands take --json for tools and agents, --root <dir> for the repository root, and --spec-root <dir> to override spec_root. Run sj <command> --help for the full list.

Proof

sj trace

Map spec scenario IDs to tests; list gaps and orphans. A FOR ALL scenario whose linked tests are all example tests prints not-property <ID> <test>... and is listed under not_property in --json; a FOR ALL scenario with no test is a gap. Each test in --json carries its package, suite and whether it's skipped (.skip, .todo, .fixme, @pytest.mark.skip, Rust #[ignore]), and whether it's a property test ("property").

--strict
Exit 1 when there are gaps or orphans, or any not-property scenario. With a baseline, only gaps and orphans it doesn't list and stale entries count; the baseline never accepts a not-property scenario.
--write-baseline
Write every current gap and orphan to <spec_root>/trace-baseline.txt, dropping stale entries, and print baseline: N entries → <path>. With --json or --strict it exits 2 and writes nothing.

sj gate

CI check: every changed scenario tested, red on base, green on head. A pass sums the evidence, as in gate: pass — 2 scenarios proven (1 red:assert, 1 green:linked). --json lists linked scenarios in proven with "red": "green:linked", and --format markdown under Linked existing behaviour. Proven FOR ALL scenarios are counted after the evidence kinds, as in gate: pass — 2 scenarios proven (2 red:assert; 1 property), and each proven entry in --json carries "property": true or false. When a property test fails its assertion on base, the gate shows the shrunk input it printed (proptest minimal failing input:, Hypothesis Falsifying example:, fast-check Counterexample:), on one line of at most 200 characters plus …: the text report prints info counterexample PAY-020 pay_020_refund_never_exceeds_charge: charge = 100, refund = 101, --json adds "counterexample": {"test": …, "input": …} to the proven entry, and --format markdown shows red:assert (counterexample: charge = 100, refund = 101) as the evidence. A missing or unreadable counterexample never changes the result.

--base <ref>
Base to compare against, e.g. origin/main. A ref that doesn't resolve exits 2 with a hint about fetch-depth: 0.
--since <commit>
Check commit history instead: every feat(ID) commit needs an earlier test(ID): red.
--allow-unverifiable
Warn instead of failing when a test can't run on base.

sj test [scope]

Run every suite and print failures only. A green run is one line; each failure shows its scenario IDs and the first 20 lines of output. A compile error is build failed, never an empty run. Records the run in the ledger.

scope
A scenario ID (AUTH-003), a package (apps/api) or one suite (apps/app:playwright). Omit to run everything.
--no-ledger
Don't record this run.

sj ledger [ID]

Per scenario: the latest result, and whether red-before-green is proven. When the scenario's latest red record holds the counterexample its property test printed, it follows the status, as in proven PAY-020 latest passed (counterexample: charge = 100, refund = 101); a later red record without one clears it.

--json
scenarios (id, latest, proven, and counterexample when there is one) and skipped, the number of unreadable lines.

sj gain

Bytes saved. sj test, sj verify, sj next and sj status each record, per run, the bytes they printed and the raw bytes they stand in for (the runners' output, or the change files) in .specjutsu/ledger/gain.jsonl. Nothing is recorded with sj test --no-ledger or outside a git repository, and recording never changes output or exit codes. sj gain prints one line per command (runs, printed bytes, raw bytes, % saved) and a total with the tokens saved, estimated as (raw − printed) / 4. specjutsu never calls a model; the numbers are bytes, a proxy. Unreadable lines are skipped with a warning on stderr, and with no records it prints no gain records yet.

test   2   500  50000  99%
next   1  1000   4000  75%
total  3  1500  54000  97%  ~13125 tokens saved
--json
commands (command, runs, printed, raw, saved_pct), total, which adds tokens_saved, and skipped, the number of unreadable lines. With no records, commands is empty and the totals are zero.
--since <time>
Only records at or after an RFC 3339 timestamp, e.g. one session.
--reset
Delete the records and print removed N gain records.

Project setup

sj init

Write specjutsu.toml and create the spec folders.

--agents <list>
Install agent adapters: claude, codex, cursor, cline, copilot, gemini, windsurf, kiro, antigravity, agents-md, or auto for the agents the repo already has files for. --remove-agents <list> removes them.
--global
With --agents or --remove-agents: install or remove only the skills, in ~/.claude/skills and ~/.agents/skills, for every project.
--force
Replace an existing specjutsu.toml.

sj adopt

Detect an existing project's packages and runners and write specjutsu.toml. Never runs a tool. A non-Cargo suite gets a support glob, <folder>/**, for every helper folder (testing, test-utils, test-helpers, testutils, fixtures, __fixtures__, mocks, __mocks__) in its package that its tests globs don't cover; a suite with none gets no support key. Folders under a tests folder are left out, since the gate always overlays them. Each glob gets a note on stderr, note support: apps/api/src/testing/** (not source; overlaid on base; remove it if this folder holds product code). A helper folder it can't read stops it with the error.

--dry-run
Print the config instead of writing it.
--force
Replace an existing file.

sj doctor

Check the project file, packages, runner executables and spec folders, one problem per line, then one line per installed agent and a skills: line saying whether the skills are in the project, global or both. Never installs anything.

sj update

Regenerate installed agent adapters. A file you edited by hand is kept and reported, and the command exits 1.

--force
Replace hand-edited files too.
--dry-run
Print one write, keep or remove line per file and change nothing; adapters up to date when there is nothing to do. Exits 0.
--json
With --dry-run: {"files": [{"path", "action"}]}.
--global
Refresh the skills installed with sj init --global instead of the repository's.

sj completions <shell>

Print a completion script for bash, zsh, fish, powershell or elvish to stdout. Any other shell exits 2. See Install for where to save it.

sj ids [--write] [target…]

List scenarios without IDs and the IDs they would get; exits 1 when there are any. A prefix derived from a folder name longer than six letters ends the list with hint: distribution would use DISTRIBUTION; sj ids prefixes --write maps it to DIST.

A delta copy without an ID gets the ID of its specs/ scenario, matching a requirement renamed in the same change by its old name. A specs/ scenario without an ID takes the ID its copy in an open change's MODIFIED requirement already has, matched by capability, requirement and scenario name (a requirement renamed in the same change matches by its old name). When another scenario already uses that ID, or copies in two open changes disagree, it gets a new number and a note: line names the scenarios involved, as in note: copies disagree: STAFF-057 … , STAFF-058 …; Role change is recorded (openspec/specs/staff/spec.md:6) gets STAFF-100; give the delta copies STAFF-100. Update the delta copies to match.

target
A capability name, or a path to a spec file or folder, resolved against --root or absolute. Each selects whole capabilities, their specs/ files and their copies in open changes; every other file is left alone. The prefix check covers every capability whose prefix a selected one uses, fully numbered ones included, so a collision between two other capabilities doesn't stop the run. When listing a target, a collision that involves a capability being numbered prints as a note: capabilities … both use prefix … line instead of stopping; numbering still covers the whole spec root. A target that selects nothing exits 2 and lists the known capabilities. A capability named prefixes can only be targeted by path.
--write
Insert them, changing only the headings.
--json
assignments with id, name, file and line, plus a note object (kind taken with copy and by, or disagree with copies) when there is one.

sj ids prefixes

Print an [ids.prefixes] table with a short prefix for every capability folder, sorted; writes nothing. A mapped prefix is kept, then the prefix a capability's IDs already use. Otherwise the folder's letters, uppercased: six or fewer kept whole (gate → GATE), longer cut to four (distribution → DIST). Clashing suggestions are lengthened together until they differ (transactions → TRANSA, transfers → TRANSF). When names run out of letters and still clash (bill beside billing = "BILL"), it exits 2 naming both capabilities and the prefix, with or without --write, and writes nothing; map one by hand. Run it before sj ids --write.

--write
Append the missing lines to [ids.prefixes] in specjutsu.toml (creating the table at the end if needed), change no other byte, and print added N prefixes to specjutsu.toml. Exits 2 without a specjutsu.toml (run sj init), and, changing nothing, when it can't find a table to splice into, printing the lines to add by hand. sj ids --write prefixes and sj ids --json prefixes exit 2.

Authoring

sj spec new <change>

Create changes/<change>/ with proposal.md, design.md, tasks.md and specs/, and print the next free ID per prefix.

sj spec list

One line per open change: tasks done, scenarios added or modified.

sj spec show <item>

Print one scenario, change or capability. Looked up as a scenario ID, then an open change, then an archived change (folder name, or bare name when only one matches), then a capability. A scenario prints with its requirement, steps, mapped tests and latest ledger result; a capability prints its spec.md unchanged. An unknown item exits 1 and suggests near names.

--json
The same data, with kind set to scenario, change or capability. A scenario has "property": true when it has a FOR ALL step, and false otherwise.

sj spec validate [change]

Scenario IDs and steps, requirement wording, delta structure, and that every task names its scenarios. Each problem has a file and line. When a MODIFIED scenario's original in specs/ has no ID, it says to run sj ids --write <capability> first: as a warning, STAFF-057 Role change is recorded: specs/staff/spec.md has this scenario without an ID; run sj ids --write staff first, or, when the delta scenario has no ID either, appended to its missing-ID error. When both have IDs and they differ, it warns STAFF-057 Role change is recorded: specs/staff/spec.md has this scenario as STAFF-100; give the delta copy STAFF-100. A FOR ALL step after WHEN is an error: PAY-021 FOR ALL step must come before WHEN (<file>:<line>).

--strict
Fail on warnings too.

sj spec check <change>

Scenarios no task names, tasks naming unknown IDs, and [NEEDS CLARIFICATION] markers.

sj spec archive <change>…

Merge the deltas into specs/ (same bytes as openspec archive) and move the change to changes/archive/YYYY-MM-DD-<change>/. Several names archive together, in name order: if any one is refused, nothing is written and every problem is listed. Two changes that modify, remove or rename the same requirement are refused.

--all-done
Archive every open change with at least one task and all of them done; nothing to archive when there are none.
--force
Archive despite validation errors and open tasks. Conflicts between changes are refused anyway.

sj spec infer <path>…

Draft a [keep] scenario for every untraced test in suite files under the paths (resolved against --root, or absolute): tests with no scenario ID in their name, title, spec: comment or @pytest.mark.spec marker. A dry run by default: one line per test, <ID> [keep] <heading> (<file>:<line>), then N tests drafted, with , L linked and S skipped left out when it left any out. Writes nothing. Exits 2 with no untraced tests under <paths> when there are none. See Specs from existing tests.

Headings come from the test name: a leading test word dropped, _ and - turned into spaces. A pytest class keeps each class name minus a leading Test word; JS and TS titles are kept as written. IDs follow the sj ids rules: an [ids.prefixes] entry wins, numbering continues after current, open-change and archived IDs and after any number with that prefix a scanned test already carries in its name or spec: comment, and a colliding prefix or a capability with no letters exits 2. A test whose name already carries an ID with the capability's prefix (billing_007_named_early) keeps that ID; when another scanned test carries it too, or a current, open-change or archived scenario ever used it, the run exits 2 naming the test and the ID and asks for the test to be renamed. Drafts are listed in file order.

--capability <name>
The capability the drafts belong to. Without it, the nearest folder above the test file that isn't tests, test, __tests__, spec, unit, integration, e2e or src (any case), kebab-cased. One run drafts for one capability: tests whose folders name different capabilities, or none, exit 2 with a hint to pass --capability. A value that isn't kebab-case exits 2 with capability `<name>` must be kebab-case before anything is written.
--write
Create <spec_root>/changes/<change>/ with proposal.md, tasks.md and specs/<capability>/spec.md: one requirement per test file, WHEN and THEN as [NEEDS CLARIFICATION: … — see <file>:<line>] markers that sj spec check reports; each <line>, and each line it prints, is where the test is once the comments are in. A requirement name already used by the capability's spec or an open change's delta for it gives way to the file's path in words, and the capability is listed as modified when its spec exists or an open change adds it. Prints created <spec_root>/changes/<change> after the count line. Insert // spec: <ID> or # spec: <ID> above each test's first attribute, decorator or declaration line, changing no other byte. Refuses an existing change folder, and leaves nothing behind on an error. Once the markers are replaced, the change passes sj gate as green:keep.
--change <name>
The change to write; default infer-<capability>.

Agent loop

sj status [change]

At most five lines per open change: tasks done, scenarios by evidence (proven, green-unproven, red, untested), and the next task.

sj view

A one-screen dashboard in at most 40 lines: capabilities with scenario counts, open changes with tasks and evidence, evidence totals, orphan tests and archived changes. Reads files and the ledger only; never runs tests.

--json
capabilities, changes, totals, orphans and archived.

sj next [change]

The next task, the text of each scenario it names, the files changed since the merge-base, principles.md, and a sj test <ID> command per scenario.

--parallel
List open [P] tasks in batches that share no test file.
--base <ref>
Base for changed files.

sj task done <change> <task>

Tick the task's box and change no other byte. In strict mode it refuses unless every scenario the task names is proven, and refuses a FOR ALL scenario whose tests are all example tests, even after red-before-green (not-property <ID> <test>, as sj verify prints it); guided and advisory modes tick the box and print the same lines as warnings. Like sj verify, it needs a red run only for added and modified scenarios. It always judges against the default branch, never --base, and when it can't classify the scenarios it warns cannot classify scenarios against the merge-base, so every one needs a red run and every FOR ALL one a property test: ….

sj verify [change]

The local check before a PR: the change's scenario tests, unproven scenarios, FOR ALL scenarios with only example tests (not-property <ID> <test>, as in the gate; a red-then-green example test doesn't prove them), orphans, sj spec check problems, and the gate's rules against the merge-base, without red-on-base. The gate's baseline rules apply too: orphans the base's baseline lists aren't problems, and entries the branch adds without a config exemption are baseline-added <entry> problems.

Scenarios are classified against the merge-base as the gate does, and only added and modified ones need a red run. Unchanged scenarios, such as one copied without edits into a MODIFIED requirement, and implemented ones need only a passing latest run; their tests still run and a failure is still reported. An implemented scenario with no red-before-green in the ledger doesn't count as covering a source change, so a change that only adds its test and edits source gets unspecified change. On the default branch itself (the merge-base is HEAD), every scenario needs a red run.

--base <ref>
Base to compare against.

Migration

sj import speckit

Preview converting Spec Kit's specs/NNN-*/ features to the OpenSpec layout. --write converts; it never touches specs/ or .specify/.

sj migrate --from <tool>

Replace openspec, speckit or superpowers (repeatable). A dry run unless --write, which needs a clean git tree and leaves the changes uncommitted.

--diff
With the preview, print a unified diff of every file it would create or change. Can't be combined with --write.
--write
Apply the plan, record an undo manifest and end with rollback: sj migrate --undo.
--undo
Put back what the last --write changed. Takes no --from. See Migrating from other tools.

Migrating from other tools

sj migrate replaces the old tool in one step, so two workflows don't compete for your agent. Every run writes specjutsu.toml if it's missing, installs the Claude Code adapter, then prints sj doctor and sj spec validate. Review with git diff; undo with sj migrate --undo.

FromWhat sj migrate does
openspecKeeps openspec/ as the spec root and gives every scenario an ID, first pinning the short prefixes sj ids prefixes suggests (DIST-001, not DISTRIBUTION-001). Moves config.yaml's guidance to principles.md. Removes OpenSpec's generated skills and /opsx commands; your own skills stay.
speckitImports every feature, then removes .specify/, the imported specs/NNN-*/ folders and the agent files Spec Kit's manifests list.
superpowersRemoves the plugin, its marketplace and its permission rules from .claude/settings.json, keeping every other byte. Lists files under docs/superpowers/ for you to review.

Preview, apply, undo

The preview lists every file it would create, change or remove; the .claude/settings.json line says your hooks stay, as in change .claude/settings.json (adapter) (merged: 1 existing hook kept). --diff adds a unified diff per file, a new file diffed against nothing. The preview runs on a copy without gitignored files, so a step that reads one, such as a gitignored .claude/settings.json, can preview differently from the write.

$ sj migrate --from openspec --from superpowers --write
…
git: 20 created, 2 changed, 0 removed
rollback: sj migrate --undo

$ sj migrate --undo
migrate: undone (2 files restored, 20 deleted; left uncommitted)

--write records the start commit and every file it touched, gitignored files included, with its hash and its content before the write, in sj-migrate-undo.json in the git directory, so it's never committed. sj migrate --undo restores changed and removed files to their content before the write, byte for byte, deletes created files and the folders they leave empty, deletes the manifest, and touches nothing else: files you made since stay. It works after you commit the migration, and leaves the result uncommitted. It refuses, exiting 2 and changing nothing, when a recorded file was edited since, naming each one; with no manifest it says there is nothing to undo. Limits: a restored file doesn't get its executable bit back, and an empty folder that held created files goes even if it existed before.

What changes for you

  • Your agent stops reading folders. sj status answers "where am I" in a few lines; sj next returns only the current task, its scenarios and the exact test command.
  • "Done" is checked, not claimed. In strict mode sj task done refuses to tick a task until the ledger shows the tests of its added and modified scenarios went red, then green.
  • TDD is enforced, not requested. The pre-edit hook blocks source edits before a failing test exists. Writing the test is always allowed.
  • Your specs don't move. OpenSpec folders stay where they are; Spec Kit features become the same layout.

FAQ

Does specjutsu call an AI model?

No. It's a deterministic binary. Your agent calls it; it never calls your agent or any LLM.

Which languages work today?

Rust (cargo test), TypeScript and JavaScript (vitest, Jest, Playwright) and Python (pytest), plus any runner that writes a JUnit XML report through a junit suite with your own command. Native test discovery for Go, dotnet, PHPUnit and RSpec is on the roadmap.

Can I adopt it in an existing repo?

Yes. Run sj adopt and sj ids --write, or sj migrate if you're on OpenSpec, Spec Kit or Superpowers. Only scenarios a change adds or modifies must be tested; existing untested scenarios are warnings. With thousands of them, or old orphan tests, commit a trace baseline so each PR shows only what it adds. Run sj ids prefixes --write before sj ids --write for short IDs.

Keeping OpenSpec alongside? Run sj ids --write <capability> before you modify a capability, so the MODIFIED copy and its original share a name for openspec validate --strict. Declare test helper folders as support (sj adopt does it for the common names); support files aren't source and are overlaid on base, so keep product code out of them. A test added for behaviour that already existed shows as green:linked and passes.

Does it work in a monorepo?

Yes. Each package in specjutsu.toml has its own suites, and a file belongs to the package with the longest matching path. sj test apps/api runs one package; the gate runs red-on-base per suite.

Do my tests have to live in tests/?

Only Rust's. Red-on-base overlays every changed file that matches a suite's tests globs, so co-located *.test.ts files work. Rust tests inline in a source file can't be moved without the new code, so they're reported as unverifiable.

Is the local ledger trusted by CI?

No. A local file is easy to forge, so CI recomputes red and green itself with red-on-base. The ledger is local evidence for the agent loop, the pre-edit hook and strict mode.

Can I check red-before-green on work I've already done?

If you used test(ID): red and feat(ID): green commit subjects, yes: sj gate --since <first-commit> checks the history.
